# High — wrong results, data loss, crashes on user data

## SIP distortion is fitted in the target frame and applied in the reference frame
Severity: High — any rotation between frames corrupts the correction; a meridian flip (180°) doubles the distortion instead of removing it. The `wide_field()` presets lift the rotation limit.

- [ ] `lumos/src/stacking/registration/distortion/sip/mod.rs` `SipPolynomial::fit_from_transform` — fit targets are `t − T(r)`, a displacement in *target* coordinates; `SipPolynomial::correct` / `WarpTransform::apply` add the polynomial to the *reference* point before `T`, giving `T(r + c(r)) = T(r) + L·c`. This is right only when the linear part `L` is the identity; the residual left after correction is `|(L − I)·d|` (0.17·|d| at 10°, 2·|d| at 180°). Fit `L⁻¹·(t − T(r))`, or apply the model after `T`.
- [ ] `distortion/sip/tests/*.rs`, `registration/tests/sip_distortion.rs` — every SIP test uses `Transform::identity()` or a pure translation, the one case where `L = I`, so the mismatch is never exercised.

## Registration accepts a transform supported by 2–4 stars as excellent
Severity: High — a minimal-sample transform has near-zero RMS, clears both the Auto bar and `max_rms_error`, and a wrong registration is reported as a good one.

- [ ] `lumos/src/stacking/registration/mod.rs` `register` — `config.matching.min_matches` ("Minimum matched star pairs to accept") gates only the `match_triangles` output; nothing compares `num_inliers()` with a floor afterwards. RANSAC returns once `best.inliers.len() >= min_samples` (2 for Euclidean, 4 for homography), `recover_matches` guarantees only "never fewer", and the final `AccuracyTooLow` gate is on RMS, which is smallest exactly at the minimal sample size.
- [ ] `lumos/src/stacking/registration/result/mod.rs` `RegistrationResult::quality_score` — `QUALITY_MIN_INLIERS = 4` is the only use of an inlier count; it feeds a log line in `pipeline/align.rs` and gates nothing.

## Deblending runs on sky-included pixel values
Severity: High — prominence, the threshold ladder and the contrast test change with the sky level, not with the source.

- [ ] `lumos/src/stacking/star_detection/detector/stages/detect/mod.rs` `DetectResult::from_image` — `extract_and_filter_candidates(pixels, …)` passes the raw grayscale plane to both deblenders; `stats.background` is in scope, and nothing upstream subtracts the sky.
- [ ] `lumos/src/stacking/star_detection/deblend/local_maxima/mod.rs` `find_local_maxima` — `min_peak_value = global_peak.value * min_prominence` is a fraction of sky plus peak. A 0.02 star on a 0.1 sky: every pixel (≥ 0.1) clears 0.3 × 0.12 = 0.036, so every noise maximum in the wings `min_separation` apart becomes a peak.
- [ ] `lumos/src/stacking/star_detection/deblend/multi_threshold/mod.rs` `deblend_multi_threshold` / `build_deblend_tree` — the ladder runs from the component's raw minimum to its raw peak: on a sky pedestal the exponential levels compress into `sky·(1…1+peak/sky)`; on near-zero sky `low` is floored to `high·1e-6`, putting most levels below the sky. `DeblendNode::flux` sums raw values, so every branch carries `sky·area` and the `min_contrast·root_flux` test favours large branches. SExtractor runs both the ladder and the contrast test on background-subtracted flux.

## FWHM auto-estimation measures on the minimum stamp
Severity: High — the estimate that sets the matched filter and the final stamp size is biased low for wide stars.

- [ ] `lumos/src/stacking/star_detection/detector/stages/fwhm/mod.rs` `from_bright_stars` — calls `measure::measure(…, 0.0)`, so the stamp radius clamps to `MIN_STAMP_RADIUS = 4` (9×9) and the `refine_centroid` weighting σ to 1.0; the configured `fwhm.expected` seed is ignored. Re-running the windowed-covariance path on noiseless Gaussians at r=4 gives FWHM 5→4.89, 6→5.58, 7→6.05, 8→6.38, 10→6.78 (exact at the radius `compute_stamp_radius` would pick). `FWHM_MAX = 20` can never be reached. Seed the first pass with `expected`, or iterate the stamp to the measured width.

## The Gaussian profile fit is axis-aligned but overrides eccentricity
Severity: High — diagonally elongated stars pass the eccentricity filter under `GaussianFit` (the `high_resolution` preset).

- [ ] `lumos/src/stacking/star_detection/centroid/gaussian_fit/mod.rs` `Gaussian2D` — parameters `[x0, y0, amp, σx, σy, bg]` have no rotation term; a star elongated at 45° fits with `σx ≈ σy`.
- [ ] `lumos/src/stacking/star_detection/centroid/mod.rs` `measure_star` — `fit_eccentricity = sqrt(1−(σmin/σmax)²)` replaces the rotation-invariant covariance eccentricity, so that star reports ≈0 against `max_eccentricity = 0.5`. `fit_fwhm` is the geometric mean of axis-projected sigmas while the moments path uses `sqrt(trace/2)` — two FWHM definitions. The rotated-ellipse tests in `centroid/tests/robustness.rs` exercise only moments.

## Frame validation differs by entry point, and the spill tier drops null masks
Severity: High — the same frames stack differently depending on which entry point loaded them and on how much RAM was free.

- [ ] `lumos/src/stacking/frame_store/mod.rs` `StoredImage::spill` / `StoredImage::load` — only channels and metadata are written; `nulls` is dropped and `load` rebuilds through `from_planar_channels` (`nulls: None`). On the RAM tier `WarpBuffers::warp_into` takes the `MaskedWarp` branch; on the spill tier (`FrameTier::hold` → `PipelineFrame::Spilled`) the median fill under every null enters the warp, the reference frame and `FrameStats::measure` as real data, and the MAD understates the noise. `CfaFrameInfo::may_carry_nulls` shows masked mosaic FITS lights are expected.
- [ ] `lumos/src/stacking/combine/cache/loader/mod.rs` `load_and_cache_frame` (reuse branch) — reused `coverage`/`confidence` planes are mmapped from disk and never pass `validate_frame_quality`, the function `FrameQuality`'s doc names as where spilled planes are held to the pairing invariant (`source_noise_variance` divides by confidence).
- [ ] `lumos/src/stacking/combine/cache/mod.rs` `from_stored_frames` / `from_stack_frames` — the two in-memory constructors run the per-frame validation in different orders (domains first vs last; geometry by sample count vs width/height). One `validate(frames, dimensions, cancel)` called by all three constructors removes the "which entry point checks what" matrix.
- [ ] `lumos/src/stacking/calibration_masters/mod.rs` `CalibrationMasters::from_images` — `prepared_flat::subtract` subtracts the flat-dark/bias from the flat without checking that they share a CFA pattern; `validate_against_light` compares each master to the light only.

## A disabled producer's stale digest keys its consumer's cache
Severity: High — a quietly wrong cache hit: a value computed with an input the run no longer delivers is served as current.

- [ ] `scenarium/src/execution/cache/runtime/mod.rs` `RuntimeCache::node_digest` (Bind arm) — folds `self.slots[addr.node_idx].current_digest?` for every `Bind`, whether or not the producer runs. `stamp_digests` re-stamps only `RunSchedule::executing()`, and a disabled producer never enters `process_order`, so its slot keeps the digest of the last run it was enabled in. A pure consumer reading it on an *optional* input stays runnable (`RunSchedule::input_missing`), `collect_inputs` hands it `Unbound`, but its digest equals the one it had with the producer live; a cached consumer (`Ram`/`Both` resident, or a `Disk` blob) then reuses the old value. A never-stamped producer leaves `None`, so the consumer never caches. Fold `InputTag::Unbound` for a producer whose schedule state is not runnable, with the same predicate `collect_inputs` uses. Latent in darkroom today (`NodeCtx::can_disable` offers the chip on sinks only); `engine/tests/disabled_nodes.rs` covers only the cold run.

## WCS evaluates invalid or unprojectable input instead of refusing it
Severity: High — each case returns a plausible wrong coordinate with no error (all confirmed by probe).

- [ ] `fits-well/src/wcs/projection/mod.rs` `Projection::project` — zenithal and perspective branches check only that the output is finite. TAN at θ < 0, SIN on the far hemisphere, AZP/SZP behind the horizon (`denom ≤ 0` never tested) return an (x, y) belonging to a different sky point. Probe (`RA---TAN`/`DEC--TAN`, CRVAL 0,0): `world_to_pixel([120,0])` → `Ok([-99.24, 0])`, whose `pixel_to_world` is `[300, 0]`. wcslib returns `PRJERR_BAD_WORLD`. Each projection needs its native-latitude domain test.
- [ ] `fits-well/src/wcs/celestial_pole.rs` `CelestialPole::from_fiducial` — the candidates `β ± acos(..)` range over (−π, 2π] and (−2π, π] and are range-tested unwrapped, so a valid `5π/3 ≡ −60°` is discarded. Probe: CAR, CRVAL2 = −30 gives δp = +60° for both `LATPOLE = 90` and `−90`. wcslib's `celset` wraps to [−180, 180] before choosing the candidate nearest LATPOLE. The `(false, false) => c1.clamp(..)` arm picks an arbitrary pole when none is valid; wcslib reports invalid parameters there.
- [ ] `fits-well/src/wcs/mod.rs` `Wcs::from_header_with_context` (celestial branch) — a lone `RA---TAN` with no latitude partner gets `AxisTransform::Linear` and is not marked unsupported (only an unknown projection code is). Probe: `RA---TAN` + `FREQ` → `unsupported=[]`, linear values returned.
- [ ] `fits-well/src/wcs/projected_celestial_axes.rs` `CelestialAxisPair::find` — pairs the first longitude-like axis with the first latitude-like axis without checking that they belong to one system. Probe: `RA---TAN` + `GLAT-TAN` is accepted and evaluated.
- [ ] `fits-well/src/wcs/mod.rs` `Wcs::axis_world` — evaluates `axis_transforms[axis]`, the placeholder `Linear` for celestial axes, and never consults `self.celestial`. Probe (TAN, CRVAL 150,60): `axis_world(0, [30,20])` → `180`, while `pixel_to_world` gives `219.31`. Its only caller (time) happens not to hit it.

## WCS unit scaling: unknown angle units read as degrees, and the public axis view mixes units
Severity: High — a wrong scale with no error, and a public metadata view that reads wrong.

- [ ] `fits-well/src/wcs/mod.rs` `unit_to_degrees` — the `_ => 1.0` arm treats every unrecognised unit as degrees, including valid FITS units such as `mrad` and any numeric multiplier (`10**-3 deg`). Probe: `CUNIT1/2 = 'mrad'`, CDELT 1 maps pixel 1 to ≈1° instead of 0.0573°. The spectral path errors on an unconvertible unit.
- [ ] `fits-well/src/wcs/wcs_axis.rs` `WcsAxis` / `Wcs::from_header_with_context` — `crval` is stored *after* CUNIT normalization (celestial × `unit_to_degrees`, spectral × `unit_scale`), while `cunit` is the declared string, cloned unchanged. `view().axes[i]` therefore reports CRVAL 1.0 with CUNIT `'arcsec'` for a declared CRVAL 3600 arcsec. The doc claims `cunit` is "normalized only where the transform requires"; it is never normalized. `AxisWorld { cunit, value }` has the same mismatch for LOG/spectral axes (value in SI, unit as declared).
- [ ] `fits-well/src/wcs/mod.rs` `unit_to_degrees`, `fits-well/src/wcs/axis/spectral_kind.rs` `prefixed_unit`/`length_scale`/`energy_scale`, `fits-well/src/time/mod.rs` `time_unit_seconds` — three parsers for "[multiplier][SI prefix]base": the angle one ignores `unit::split_numeric_multiplier`/`si_prefix`, the spectral one strips a suffix and matches the prefix exactly, the time one loops over `SI_PREFIXES`. One `unit.rs` resolver over a base-unit table removes the drift.
- [ ] `fits-well/src/unit.rs` `parse_multiplier_prefix` — `10.0_f64.powi(exponent)` is inexact for exponents ≤ −23 (probe: `10**-24 m` → `1.0000000000000001e-24`). Parse `1e{exp}` or use exact powers.

## Compressed tables written by fits-well cannot be read back
Severity: High — round-trip failure for a documented feature (probe).

- [ ] `fits-well/src/compress/table/mod.rs` `uncompress_table` → `VlaColumn::cell` → `Column::validate_vla_tdim` — §10.3.1 says the copied `TDIMn`/`TSCALn`/`TZEROn`/`TNULLn` apply to the *uncompressed* data; `compress_table` copies them correctly, but the read path parses the container as an ordinary BINTABLE and checks the compressed byte count against the original `TDIMn`. Probe: a `100J` column with `TDIM (10,10)` written with `Compression::Rice` fails `read_compressed_table` with `KeywordOutOfRange { name: "TDIMn" }`.

## Image conversion and SIMD kernels return wrong or CPU-dependent pixels
Severity: High — public API returns wrong pixels; results depend on the CPU and on a sample's position in its row.

- [ ] `imaginarium/src/image/mod.rs` `Image::convert_to` / `imaginarium/src/image/conversion/mod.rs` `convert_image` — `convert_to` allocates `Image::new_black(desc)` and calls `convert_image`, which returns early when `from_fmt == to_fmt`, so `img.convert_to(img.desc().color_format)` yields an all-zero image while the doc promises "a valid (if pointless) full copy". Every caller (`lens/src/image/nodes/io.rs`, `lens/src/image/nodes/processing.rs`, `lumos/src/io/image/linear.rs`) guards against it first; no test covers it. Copy in `convert_to`; assert differing formats in `convert_image`.
- [ ] `imaginarium/src/image/conversion/simd/sse.rs` `convert_u16_to_u8_row_sse2`, `simd/neon.rs` `convert_u16_to_u8_row_neon` (AVX2 hands its tail to SSE2) — the vector body computes `v >> 8` like the scalar reference, the sub-vector tail computes `v / 257`. They differ on 32640 of 65536 inputs (`0xFF00`: 255 vs 254), so the last `len % 16` samples of every row convert differently. Have the tail call the scalar reference, as `luma_tail` and the blend `rgba_tail` do.
- [ ] `imaginarium/src/image/conversion/simd/{sse.rs,avx.rs,neon.rs}` `convert_f32_to_u8_row_*` / `convert_f32_to_u16_row_*` — kernels and tails multiply in `f32` and then round; the scalar reference `impl_convert_float_to_int` multiplies in `f64`. An exhaustive sweep of `f32` in `[0, 1]` finds 128 (u8) and 32640 (u16) differing inputs, where the f32 product lands exactly on `.5` and rounds to even. Contradicts the precision section of `simd/mod.rs`.
- [ ] `imaginarium/src/image/conversion/simd/tests/mod.rs` `create_test_image_u16` / `create_test_image_f32` — `simd_matches_scalar_reference` feeds only `k*257` and `k/255`, exactly the inputs where both divergences vanish.

## GPU blend and contrast dispatch fails on the image sizes the device is configured for
Severity: High — a wgpu validation error on any image over ~64 MiB.

- [ ] `imaginarium/src/ops/blend/gpu.rs` `apply`, `imaginarium/src/ops/contrast_brightness/gpu.rs` `apply` — `dispatch_workgroups(total_words.div_ceil(256), 1, 1)` exceeds the default `max_compute_workgroups_per_dimension = 65535`, which `Gpu::new` does not raise; a 24 MP `RGB_F32` frame needs 281 250 workgroups. `Gpu::new` (`gpu/mod.rs`) allows 1 GB buffers "for astrophotography images". Dispatch in 2-D or grid-stride in the shader.
- [ ] `imaginarium/src/gpu/mod.rs` `Gpu::new` — `required_limits` hard-codes 1 GB buffer and binding sizes without clamping to `adapter.limits()`, so `request_device` fails outright on a smaller adapter.

## Untrusted data reaches code-contract asserts and panics
Severity: High — user files and user-wired graphs crash the process or the worker instead of producing an error.

- [ ] `imaginarium/src/drawing.rs` `draw_circle` / `draw_dot` — for a shape entirely left of or above the image, `((cx + r).ceil() as i32).min(width as i32 - 1) as usize` is negative and wraps to ~2^64; the distance test rejects every pixel, so the loop runs essentially forever. Clamp in `i32` and return early on an empty box.

# Medium — wrong in edge cases, duplicated truths, hot-path waste

## Typed ids are parsed from strings at run time through a conversion that panics
Severity: Medium — per-frame UUID parsing on hot paths, a `From` impl that panics on bad input, and ids that bypass the `uuidgen` rule.

- [ ] `common/src/macros.rs` `id_type!` — `From<&str>` / `From<String>` panic on an invalid UUID. `From` is the infallible conversion; `FromStr` already exists for the fallible one, and `const fn from_u128` exists for literals. Remove the two `From` impls so every literal becomes a `const` and every parse a `parse()`.
- [ ] `darkroom/src/core/preview/mod.rs` `is_preview` — `func_id == PREVIEW_FUNC_ID.into()` runs `Uuid::parse_str` on each call; callers are per node per frame (`NodeCtx::preview`, twice in `gui/pane/graph/node/widget.rs`, once in `gui/pane/graph/mod.rs`) and per stored preview per frame (`Document::holds_preview_node` via `PreviewStore::reconcile`). `registered` scans `library.funcs()` and parses once per func where `Library::by_id` is a hash lookup.
- [ ] `lens/src/image/mod.rs` `IMAGE_TYPE_ID`, `lens/src/astro/masters.rs` `MASTERS_TYPE_ID`, `lens/src/image/format.rs` `CONVERSION_FORMAT_TYPE_ID`, `lens/src/image/nodes/mod.rs` `BLENDMODE_TYPE_ID` (and their `_DATA_TYPE`s) — `LazyLock<TypeId>` over a string parse, while `ml.rs` / `fs_watch` already use `FuncId::from_u128` consts. `lens/src/config_node.rs` `NodeConfig::TYPE_ID: &str` is re-parsed on every `CustomValue::type_id()` / `config_data_type()` call. darkroom derefs `*lens::IMAGE_TYPE_ID`.
- [ ] `lens/src/image/nodes/processing.rs` `register_brightness` (`"b8c3d4e5-f6a7-4b8c-9d0e-1f2a3b4c5d6e"`) and `register_transform` (`"d3e4f5a6-b7c8-4d9e-0f1a-2b3c4d5e6f7a"`) — sequential hex runs, hand-typed rather than `uuidgen` output (AGENTS.md); the second also has an invalid RFC 4122 variant nibble.
- [ ] `lens/src/config_node.rs` `NodeConfig` (impls in `lens/src/astro/config/processing.rs`) — `IntrospectEnum` carries `TYPE_ID` on the owning type, `Introspect` structs do not, so lens adds a second trait to give `ExtractBackground`, `Denoise`, `Hdr`, `LocalContrast` their wire ids from outside; `BLENDMODE_TYPE_ID` is a lens-owned id for imaginarium's `BlendMode`. A `#[config(type_id)]` on `Introspect` lets owners carry their ids.
