# Medium — wrong in edge cases, duplicated truths, hot-path waste

## Undo coalescing has no gesture identity and re-encodes the tail every frame
Severity: Medium — separate gestures merge into one entry, merges leave phantom entries, and a held drag allocates about six times per frame.

- [ ] `darkroom/src/core/edit/step/gesture_key.rs` `GestureKey` + `darkroom/src/core/edit/action_stack/mod.rs` `ActionStack::try_merge_with_last` — the key is `Viewport` (unit variant) or `SelectionDrag(grabbed)` and nothing marks where a gesture ends. Two separate pans, a pan then a toolbar fit / zoom-reset / shortcut viewport jump, and two drags of the same already-selected node (grabbing a selected node emits no click, `gui/pane/graph/node/widget.rs`) fold into one entry. Give the key a per-gesture instance, or seal the entry on release.
- [ ] `ActionStack::try_merge_with_last` — re-appends the merged step without checking `UndoStep::is_noop`; a drag that returns to its start or a pan back within `VIEWPORT_EPS` leaves an entry that undoes nothing.
- [ ] `ActionStack::try_merge_with_last` / `append_steps` — each coalesced frame deserializes the last entry into a fresh `Vec<UndoStep>`, merges, and bitcode-serializes it back. `append_steps` passes `&mut Vec::new()` as the "reusable" scratch, and `common/src/serde.rs` `serialize_into`'s Bitcode arm ignores the scratch anyway (`bitcode::serialize` returns its own `Vec`, then it is copied). The `serialize_into` doc ("avoid per-call allocation in hot paths (e.g. undo-step coalescing)") is false for its only caller. Keep the open gesture entry decoded on `ActionStack` and pack it when sealed.
- [ ] `darkroom/src/core/edit/step/move_selection.rs` `MoveSelection::coalesce` — a new `moves` Vec per frame plus `next.moves.iter().find(..)` per member (O(k²)); both steps come from one latched `start_positions` list in the same order, so zip them or overwrite `to` in place. `OpenDocument::commit` (`batch`), `into_step`'s `MoveSelection` arm (`placed`) and `Anchor::resolve` (`moves`) add three more fresh Vecs per frame; `GraphIntent::MoveSelection { moves: Vec<(NodeId, Vec2)> }` is a tuple mirror of the step's `Vec<Move>`.

## Pixel layout is converted and copied at crate boundaries
Severity: Medium — full-frame copies on every stack, load, cache write and GPU download, on images of hundreds of MB.

- [ ] `lens/src/astro/nodes/stacking.rs` `register` — `result.product.image` is already a `LinearImage` but leaves as `Image::from(RawImage::from(&result.product.image))` (an interleave copy); coverage and weight go `Coverage → LinearImage → RawImage::from(&…)`. The next astro node deinterleaves again in `runtime::image_to_planar`. `Image::from(result.product.image)` keeps them planar.
- [ ] `lens/src/astro/nodes/stacking.rs` `register` — `AlignStackConfig.stack.quality` stays `QualityPlanes::ALL`, so the combine fills a per-channel `linear_variance` plane (~240 MB per plane per channel at 60 MP) that lens drops, and coverage/weight are produced even when `demand[1]`/`demand[2]` is `Skip`. The `.expect("coverage requested by the stacking config")` holds only by convention. Set `stack.quality` from `demand`.
- [ ] `lens/src/astro/nodes/io.rs` `register` (Load Astro Image) / `lumos/src/io/image/preview_image.rs` — `PreviewImage::from(LinearImage)` interleaves a FITS/RAW decode and the first astro node deinterleaves it again: two full copies per load. Let the preview product hand back its planes.
- [ ] `lens/src/image/codec/mod.rs` `ImageCodec::encode` / `decode` — always writes `image.interleaved()` and restores `InterleavedCpu`, so caching an astro output repacks planes and a cache hit deinterleaves again; `decode` zero-fills with `Image::new_black` before `read_exact` overwrites every byte.

## `darkroom::core` claims to be frontend-free but imports `gui` and palantir
Severity: Medium — the documented layering does not hold.

- [ ] `darkroom/src/core/mod.rs` says "No Palantir … this layer never imports from it", but `core/document/open_document/mod.rs` imports `crate::gui::relayout::Relayout` and `crate::gui::requests::{DocumentRequest, Requests}`, `open_document/replay_outcome.rs` imports `Relayout`, `core/document/mod.rs` imports `palantir::DockState`, and `core/io/preferences/mod.rs` imports `palantir::ImageFilter`. Move `Requests`/`DocumentRequest`/`Relayout` into `core::edit` (or the drain into `gui`), and either state the palantir dependency or remove it.

## Loaded documents and preferences are not held to the editor's invariants
Severity: Medium — an untrusted file can hide the graph pane for good, and a corrupt preferences file is silently destroyed.

- [ ] `darkroom/src/core/document/mod.rs` `Document::validate` — palantir's `DockState` deserialization requires only that some group holds the file's own `pinned` tab; `pinned` and `seed` come from the file. Darkroom never checks `layout.pinned() == TabRef::Graph`, that `TabRef::Graph` is present, or that the seed is `DOCK_SEED`. A layout pinning `Preferences` with no `Graph` loads, and the menu can reopen only `Preferences` (`gui/window/menu_bar.rs`).
- [ ] `darkroom/src/core/io/preferences/mod.rs` `Preferences::load` — `deserialize(..).unwrap_or_default()` with no log or status; the next `save_preferences` (any document open/save, any preference change, every close) overwrites the unreadable file with defaults. Report the parse error (`App::new` has a `StatusLog`) and do not overwrite a file that failed to parse.

## Canvas gestures: Esc does two things, two drags ignore it, and docs describe panes that do not exist
Severity: Medium — one key press triggers two unrelated reactions; several comments describe safety checks that are not in the code.

- [ ] `darkroom/src/gui/pane/graph/gesture/shortcuts.rs` `emit` — reads `ui.escape_pressed()` again and pushes `clear_selection()`, while `GraphUI::prepass` (`graph/mod.rs`) already read the same key into `self.cancelled` to abort the gesture in flight. Cancelling a rubber band (including a Shift-extend whose `base` is the existing selection) or a wire drag also wipes the selection. Deselect only from `cancelled` plus "nothing was in flight".
- [ ] `gesture/drag_anchor/mod.rs` `GroupDrag::advance` and `gesture/preview_drag/mod.rs` `PreviewDrag::apply` — never check `cx.cancelled()`, unlike Connection, Subscription, Breaker and Selection; Esc during a node drag keeps the nodes moving (and deselects them).
- [ ] `graph/canvas.rs` `outer_canvas_widget_id` / `inner_canvas_widget_id` vs the `GraphUI` doc in `graph/mod.rs` — the doc says one instance drives N canvases with per-pane ids from `GraphCtx`; both ids are fixed global hashes, `GraphCtx` carries no pane identity, and `TabRef::Graph` is a single tab. `GraphUI::appearing`'s split-view case is unreachable.
- [ ] `gesture/breaker/mod.rs` `BreakerUI::probe` (doc calls a pane check "load-bearing"; there is none), `ConnectionUI::apply`/`draw_in_flight`, `SubscriptionUI::apply`/`draw_in_flight` ("Scoped: the preview belongs to the pane holding the wire's start node…"), `selection/mod.rs` `SelectionUI.preview`/`apply`, `drag_anchor/mod.rs` `Anchor` (doc of a removed pane field glued onto `start_positions`), `classify_canvas_gesture` (refers to a non-parameter `target`), `node_menu/mod.rs`, `new_node/mod.rs`, the `graph/toolbar.rs` module doc — all narrate per-pane scoping the code does not do.
